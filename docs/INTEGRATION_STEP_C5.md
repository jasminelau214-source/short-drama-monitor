## Behavior and boundary

`ResearchExecutionSession` now accepts an explicit typed `ResearchCallJournal` adapter. The existing local journal remains supported; no environment-based activation or silent local fallback is introduced. `SupabaseCallJournal` supplies the same inspect/reserve/finish/wait/resume boundary through a fixed HTTPS PostgREST RPC. It requires a pinned nonproduction project ref and exact database instance UUID, a publishable API key and a protected Auth worker session. It explicitly refuses the known production project. It does not accept arbitrary URLs or task/model-provided configuration, use a service_role key, log credentials or automatically retry uncertain database mutations.

The official CLI generated `20261013060354_v2_isolated_call_journal.sql`. It creates five private tables: instance metadata, an administrator-managed worker allowlist, task budgets, per-call checkpoints and idempotent retry-wait events. It refuses databases containing the legacy production research/analysis tables before DDL. The migration is intentionally for a separate staging database; it is not a production cutover migration.

The exposed public RPC wrapper uses SECURITY INVOKER. Its private SECURITY DEFINER dispatcher is necessary for restricted access to private tables; it checks `auth.uid()` against the protected worker allowlist, expiry and enabled flag for every RPC. Normal authenticated users, anonymous users and service_role cannot use it as a general data endpoint. Workers have no direct table grants, cannot register or approve themselves, alter RLS or obtain dispatch owner tokens through checkpoint inspection. All tables have RLS enabled; fixed search paths put pg_temp last. No auth.uid value, user ID, password or allowlist entry is seeded by the migration. Worker setup must be performed separately by a trusted administrator after target verification.

Each mutation locks the task first, uses unique call keys and allows only one INFLIGHT call per task. Server time enforces retry backoff and charges no less than the persisted dispatch-to-outcome interval. It retains the three-attempt budget, three logical search-round ceiling, quota pause/resume and 300-second provider/backoff budget. Exact repeated finish/wait messages are idempotent; conflicting repeats fail closed. A lost finish reply can be reconciled by inspecting/reusing an already successful call without repeating the provider request. An uncertain INFLIGHT request stays held. External APIs are never called while a database transaction is held.

## Verification

Offline tests check exact project/instance binding, strict response types, credential placement, HTTPS/redirect restrictions, sanitized failures, no automatic retry and no provider dispatch after an uncertain reservation reply. Real PostgreSQL 17.11 tests apply the actual migration, call the actual Python adapter through a loopback SQL bridge and verify concurrent reservation, durable reopening, owner/authority binding, idempotent finish/wait, server-clock limits, quota resume, permission refusal, worker revocation/expiry, temp-schema shadowing, migration refusal on a legacy database and actual execution-session reuse after a lost finish reply.

The SQL bridge stubs Supabase Auth claims/roles and bypasses the HTTP gateway ONLY inside the owned disposable fixture. It is not evidence of live Auth/JWT verification, PostgREST role propagation or deployed Supabase compatibility. Official CLI database advisors run against that fixture; the initial attempt required correcting the loopback-only non-TLS connection mode. Live Supabase HTTPS always uses certificate verification and modern TLS. Advisors on a partial fixture do not replace live project advisors.

Initial test errors in the new client mocks and a PL/pgSQL CASE expression were corrected. Final proof must bind the committed candidate, include all earlier offline/PostgreSQL regressions, show no skipped tests and confirm owned clusters were stopped/removed.

The official CLI 2.120.0 archive was downloaded outside Git from the vendor's GitHub release and verified against its published SHA-256. The changelog was checked, including the upcoming removal of old CBC TLS ciphers and PostgreSQL 17.11 extension changes. This implementation uses modern Python TLS and no affected ltree, btree_gist, legacy pgcrypto encryption or custom operators. References: [database functions](https://supabase.com/docs/guides/database/functions), [API access controls](https://supabase.com/docs/guides/api/securing-your-api), [TLS change](https://supabase.com/changelog/cbc-tls-ciphers-deprecated).

Candidate code rollback is reverting the eight C5 files. For an installed staging journal, first stop its workers and disable their allowlist entries, export/checkpoint ambiguous INFLIGHT calls, and retain the journal for reconciliation. Do not delete or replay it automatically. Production needs no restoration because this stage makes no production changes.
